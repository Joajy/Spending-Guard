# PostgreSQL 백업과 복구

소비 원장과 사용자 예산은 PostgreSQL에 저장되므로 애플리케이션 이미지만 롤백해서는 데이터 손상을 복구할 수 없다. 이 절차는 운영 Compose의 PostgreSQL에서 논리 백업을 만들고, 실제 복구 전에 파일 무결성과 아카이브 형식을 확인한다.

## 백업

운영 환경 변수를 설정한 서버에서 다음 명령을 실행한다.

```bash
scripts/database/backup.sh
```

기본 저장 위치는 `backups/postgres`다. 백업은 PostgreSQL custom archive와 SHA-256 파일 한 쌍으로 만들어진다. 덤프 생성 중에는 `.partial` 파일을 사용하며, 아카이브 검사가 끝난 파일만 최종 이름으로 변경한다.

백업 파일을 서버 한 대에만 두면 서버 장애와 함께 사라질 수 있다. 생성된 `.dump`와 `.sha256` 파일은 암호화된 별도 저장소로 함께 복사하고 보존 기간과 접근 권한을 운영 환경에서 설정한다. 실제 금융 원문과 개인정보가 포함될 수 있으므로 공개 저장소나 일반 파일 공유 서비스에 올리지 않는다.

## 복구

복구는 현재 데이터베이스를 삭제하고 백업 시점으로 되돌리는 작업이다. 대상 파일과 데이터베이스 이름을 명시해야 실행된다.

```bash
scripts/database/restore.sh \
  backups/postgres/spending_guard-20260902T120000Z.dump \
  --confirm-database spending_guard
```

복구 스크립트는 다음 순서로 동작한다.

1. 백업과 SHA-256 파일이 모두 있는지 확인한다.
2. 체크섬과 PostgreSQL archive 목록을 검사한다.
3. 현재 실행 중인 백엔드, 프론트엔드와 게이트웨이만 중지한다.
4. 데이터베이스를 다시 만들고 `pg_restore --exit-on-error`로 복원한다.
5. 복구에 성공했을 때만 이전에 실행 중이던 애플리케이션 서비스를 다시 시작한다.

복구에 실패하면 부분 데이터가 사용자에게 노출되지 않도록 애플리케이션을 중지 상태로 유지한다. 원인을 확인하고 정상 백업으로 다시 복구한 뒤 서비스를 시작한다.

## 정기 실행과 복구 훈련

백업 주기는 운영 데이터 손실 허용 범위에 맞춰 정한다. 초기 단일 서버 운영에서는 매일 백업하고 최근 14일을 별도 암호화 저장소에 보관하는 구성이 현실적이다. 단, 보존 파일 삭제는 저장소 정책으로 관리하며 이 저장소의 스크립트가 자동 삭제하지 않는다.

백업 성공 로그만으로 복구 가능성을 보장할 수 없다. GitHub Actions는 임시 PostgreSQL에 기준 데이터를 저장한 뒤 백업하고 값을 변경한 다음, 실제 복구를 수행해 기준 데이터가 돌아오는지 검사한다. 운영 환경에서도 분기마다 격리된 데이터베이스에서 같은 복구 훈련을 수행한다.
