# Product Brief

## 1. 문제

사용자는 정기 구독처럼 명확한 고정비보다 배달, 택시, 쇼핑처럼 누적되는 변동 지출을 늦게 인지한다. 여러 금융 알림은 비정형 텍스트로 흩어져 있고, 단순 총액만으로는 왜 확인해야 하는지 알기 어렵다.

## 2. 제품 목표

SpendGuard는 소비 이벤트를 빠르게 수집하고 구조화한 뒤, 사용자의 예산과 과거 소비 기준으로 다음 질문에 답한다.

- 이번 달 예산이 평소보다 빠르게 소진되는가?
- 특정 카테고리 소비가 개인 평균보다 급증했는가?
- 같은 결제가 짧은 시간에 반복되었는가?
- 반복 결제 금액이 지난달보다 변했는가?
- AI가 분류한 결과를 사용자가 검토하고 수정할 수 있는가?

SpendGuard는 거래를 차단하거나 사기로 단정하지 않는다. 사용자가 확인할 만한 변화와 그 근거를 제공한다.

## 3. 목표 사용자

- 월말 전에 소비 증가를 알고 싶은 개인
- 카드·은행 알림을 받지만 가계부 입력을 지속하기 어려운 사용자
- 간단한 예산과 소비 경고가 필요한 사용자

## 4. MVP 입력원

| 입력원 | MVP | 비고 |
|---|---:|---|
| 금융 알림 텍스트 붙여넣기 | 필수 | 실제 사용 경로 |
| CSV 업로드 | 필수 | 다건 입력 |
| 합성 거래 시뮬레이터 | 필수 | 테스트·부하 측정 |
| 토스페이먼츠 테스트 웹훅 | 선택 | 상점 결제 이벤트 Adapter |
| 금융결제원 오픈뱅킹 | 제외 | 운영 연동은 이용승인·계약 필요, Port만 고려 |

토스페이먼츠는 사용자의 전체 금융 거래를 제공하지 않으므로, 전체 소비내역 수집원으로 표현하지 않는다.

## 5. MVP 기능

### 사용자

- 이메일·비밀번호 회원가입과 로그인
- 월간 전체 예산 및 카테고리별 예산 설정

### 소비 이벤트

- 단일 금융 알림 텍스트 등록
- CSV 다건 등록
- 처리 상태 조회
- 거래 목록과 상세 조회
- 승인, 취소, 환불 표현
- 사용자 카테고리 수정

### 분석

- 개인정보 마스킹
- 금액, 발생시각, 거래유형 Fast Parsing
- LLM 기반 가맹점 정규화와 카테고리 분류
- 낮은 신뢰도의 `NEEDS_REVIEW` 처리
- 알려진 가맹점 규칙 기반 Fallback

### 간단한 Risk Engine

- 월간 예산 소진율 경고
- 월 진행률 대비 예산 소진 속도 경고
- 최근 7일 카테고리 지출 급증
- 동일 가맹점·금액의 단시간 반복 결제
- 반복 결제 금액 변동

### 운영과 검증

- Transactional Outbox
- Kafka 재전달을 고려한 멱등 Consumer
- Retry와 DLQ
- 원장·Projection 대조 작업
- Postman Collection과 자동 실행 보고서
- 정확도 평가 데이터셋
- 동시성·장애·부하 테스트

## 6. 제외 범위

- 실제 금융 거래 실행 또는 차단
- 사기 거래 확정 판단
- 실제 카드번호 저장
- 운영용 오픈뱅킹·마이데이터 연동
- Kubernetes와 다중 리전 구성
- Redis 기반 분산 락
- 학습형 이상탐지 모델
- 복잡한 관리자 백오피스

## 7. 성공 기준

기능의 존재가 아니라 재현 가능한 테스트 결과로 성공을 판단한다.

- 동일 이벤트 재전달 시 원장 중복 0건
- 동시 예산 갱신 후 합계 오차 0원
- Kafka 장애 중 수집 이벤트 유실 0건
- 정의된 Risk 규칙 시나리오 적합률 100%
- 금액·거래유형 Parsing 목표 정확도 달성
- 모든 공개 API를 Postman Collection으로 실행 가능
- 프론트에서 입력, 처리 확인, 대시보드 조회, 분류 수정 가능

세부 목표와 계산식은 `docs/metrics/measurement-plan.md`에서 관리한다.
